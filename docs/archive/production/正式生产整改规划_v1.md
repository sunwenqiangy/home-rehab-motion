# Home Rehab Motion 正式生产整改规划

**版本**：V1.0  
**状态**：待实施评审  
**目标**：将当前研发/演示级系统整改为可承载真实患者数据的正式生产系统。  
**适用范围**：微信小程序、Web 管理端、主服务、动作分析服务、云基础设施、数据治理与运营流程。

---

## 1. 目标与准入边界

### 1.1 目标

正式生产环境应同时满足：

1. 患者身份、视频、报告、反馈图片及健康相关数据具备最小权限保护；
2. 上传、分析、回调、报告、通知与人工复核在异常情况下可恢复、可追踪；
3. 算法在质量不足、低置信度、模板缺失或结果异常时不输出确定性动作结论；
4. 应用可通过可复现构建部署到云上，具备监控、告警、备份与恢复能力；
5. 患者授权、数据保留/删除、操作审计、人工复核和医疗边界有明确规则；
6. 上线前完成法规适用性、个人信息保护和临床/专家验证的组织评估。

### 1.2 非目标

本规划不替代以下组织决策：

- 医疗器械分类、注册/备案及临床评价的最终法律判断；
- 医院伦理、知情同意和数据出境等合规审批；
- 云账号、网络、域名、证书、KMS 和监控平台的采购/开通；
- 专家对动作金标准、阈值及患者适用范围的最终医学确认。

系统患者端必须持续展示：

> 本系统结果基于视频图像分析，仅用于辅助训练反馈，不构成医疗诊断或治疗建议。训练中如有疼痛或明显不适，请暂停训练并及时咨询专业医疗人员。

## 2. 目标生产架构

```text
微信小程序 / Web 管理端
  │ HTTPS
  ▼
WAF / CDN / 负载均衡 / Ingress
  │
  ├─ 管理端静态站点
  └─ main-service（多副本）
       │ 私网访问
       ├─ analysis-service API
       ├─ Celery worker（独立分析队列）
       ├─ 托管 MySQL（业务、审计、任务与回调投递状态）
       ├─ 托管 Redis（缓存、Broker、短期任务态）
       ├─ 私有对象存储（患者视频、反馈图片、分析产物）
       └─ 可观测性平台（日志、指标、追踪、告警）
```

生产环境原则：

- 所有外部入口只允许 HTTPS；服务、数据库、Redis 和对象存储管理面只通过私网访问；
- 患者视频和反馈图片存放于私有 bucket，访问必须经鉴权后签发短期 URL；
- Secret Manager/KMS 管理密钥，应用仅通过运行时注入读取；
- `development`、`staging`、`production` 的数据库、对象存储、密钥、域名和监控数据严格隔离；
- 生产镜像不可变、可追溯；部署和数据库迁移均经 CI/CD 与人工审批。

## 3. 安全与访问控制整改

### 3.1 生产环境硬门禁

生产启动时必须校验并拒绝以下配置：

- `MOCK_AUTH_FALLBACK=true`；
- `AUTH_ALLOW_LEGACY_MOCK_TOKEN=true`；
- `ALLOW_SAMPLE_VIDEO_FALLBACK=true`；
- `ALLOW_MOCK_KEYPOINTS_FALLBACK=true`；
- 默认或弱 `ANALYSIS_INTERNAL_TOKEN`；
- HTTP 外部 API 地址；
- 公共访问的患者数据 bucket；
- 缺失生产数据库、对象存储或加密配置。

### 3.2 账户与权限

- 管理端登录接口只能验证既有账号，禁止首次登录自动建号；
- 角色只能读取数据库权限字段，不可由用户名、前端参数或 URL 推断；
- 管理员账号新增、启停、密码重置、角色调整走受审计的管理接口；
- 增加登录失败限流、账户锁定、强密码策略和可选 MFA/SSO；
- 患者、医护、管理员均采用最小权限；定期复核权限，离职/角色调整即时回收；
- 管理端查看/下载患者视频、报告、反馈图片及导出数据必须写入审计日志。

### 3.3 资产与隐私数据

- 禁止通过静态目录直接公开患者资产；
- 视频和图片访问必须验证患者归属或医护角色，并使用短时效签名 URL；
- 服务端执行 MIME、文件大小、视频时长、容器格式和文件头校验；
- 反馈图片执行 MIME、文件头、尺寸、数量和大小限制；
- 对象存储、数据库备份和传输链路启用加密；
- 明确原始视频、关键点、报告、反馈图片和审计日志的保留期限、删除与恢复边界。

## 4. 分析任务可靠性与状态机

### 4.1 状态机

主服务是患者可见状态的唯一真相源。推荐状态：

```text
pending → uploading → queued → processing
                              ├─ completed
                              ├─ quality_insufficient
                              ├─ review_required
                              ├─ failed
                              └─ timed_out
```

规则：

1. `completed`、`quality_insufficient`、`review_required`、`failed`、`timed_out` 均为终态；
2. 普通回调不得将终态覆盖为其他终态或中间态；
3. 每一次分析创建独立 `analysisRunId` 与幂等键；重新分析创建新运行记录，不覆写旧分析运行；
4. 回调必须校验视频 ID、任务 ID、运行 ID、签名、算法版本与状态转换合法性；
5. 患者端仅在主服务同时确认最终状态和报告就绪时进入报告页；
6. 状态迁移、重试、人工复核和失败原因均需可查询和审计。

### 4.2 回调 Outbox、重试与补偿

分析完成后执行：

```text
分析结果持久化
  → 写 callback_outbox
  → 发送回调
  → 主服务原子写报告/状态/事件
  → 返回确认
  → outbox 标记 delivered
```

- 未收到确认时按 1 分钟、5 分钟、15 分钟、1 小时、6 小时进行有限指数退避；
- 超过上限进入死信队列，并产生告警和运营待办；
- 主服务定时扫描“分析侧已完成但业务侧未终态”的任务并触发补偿；
- Redis 故障不能成为最终结果丢失原因，结果和投递状态必须落 MySQL；
- 重复回调不得重复生成报告、训练记录、通知、徽章或激励快照。

## 5. 算法安全、质量门控与人工复核

### 5.1 先判断可否评价

| 结果 | 触发条件 | 患者端表现 | 管理端动作 |
|---|---|---|---|
| `completed` | 视频质量、关键点、角度、模板和置信度均达标 | 展示辅助训练反馈、最多两条建议 | 可查看详情、按需复核 |
| `quality_insufficient` | 低光、遮挡、入镜不完整、角度错误、帧率问题、关键点不足 | 不显示动作等级，给重拍指引 | 记录具体质量原因 |
| `review_required` | 模板/特征缺失、结果冲突、异常分布、算法异常 | 显示“需要进一步确认”，不下确定性结论 | 自动进入人工复核队列 |
| `failed` / `timed_out` | 基础设施或不可恢复算法错误 | 明确重试/稍后查看路径 | 触发技术告警与补偿 |

### 5.2 硬性算法规则

- 未配置模板或特征映射时必须为 `review_required`，不得默认 `normal`；
- 低于专家确认阈值的置信度不生成“优秀/合格/需改进/无效”；
- 质量检测补齐亮度、人体入镜完整性、主要关节可见性、遮挡、拍摄角度与帧率稳定性；
- 必需维度缺失时不得使用其他维度回填总分；
- 每份报告关联算法版本、模板版本、阈值版本、质量结果、分析运行和人工复核版本；
- 上线前建立经专家标注的回归集，完成标注一致性、样本代表性、错误案例和阈值校准验证。

### 5.3 人工复核

- 复核队列展示视频、算法结果、质量原因、模板版本和历史趋势；
- 医护可选择人工修正、建议重拍、发送训练指导或归档；
- 人工修改须记录修改人、时间、依据、原算法快照和患者可见文案；
- 身体不适反馈立即走安全分流，不进入等待算法或普通反馈队列。

## 6. 可观测性、备份与安全运营

### 6.1 追踪、日志与指标

所有患者请求生成 `traceId` 并贯穿：

```text
患者请求 → main-service → 分析任务 → Celery Worker
→ callback_outbox → main-service 写入 → 通知 / 人工复核
```

最小监控集：

- API：错误率、认证失败率、P95/P99 时延；
- 上传：成功率、文件校验失败率、对象存储失败率；
- 分析：队列积压、分析耗时、成功率、质量拒绝率、低置信度率；
- 回调：成功率、重试数、死信数、未送达数、状态冲突数；
- 业务：报告可用率、人工复核积压、反馈待处理时长；
- 基础设施：数据库连接、磁盘、CPU/内存、Redis、备份成功率。

### 6.2 审计与告警

必须审计：

- 账号、角色、权限变更；
- 患者视频、报告、反馈图片的查看、下载和导出；
- 阈值、模板、算法版本变更；
- 人工复核、数据删除、数据恢复；
- 敏感配置变更和生产发布。

必须告警：

- 回调死信、队列积压、分析失败率异常、报告不可用率异常；
- 私有资产访问异常、认证失败异常、权限拒绝异常；
- 数据库/Redis 不可用、备份失败、证书即将到期；
- 关键安全配置校验失败。

### 6.3 备份和恢复

- MySQL：加密备份、保留策略、按周期恢复演练；
- 对象存储：版本控制、生命周期、跨区域/跨账号备份策略；
- Redis：为 broker 设置持久化、灾后重建和任务补偿策略；
- 每次数据库迁移在执行前完成备份，在 staging 验证后再进入生产；
- 形成 RPO/RTO 目标和明确恢复责任人。

## 7. 工程交付、测试与发布闸门

### 7.1 环境与交付

- 建立 `development`、`staging`、`production` 环境隔离；
- 每个应用服务提供 Dockerfile 和不可变镜像；
- 使用 IaC 管理云网络、私网安全组、数据库、缓存、对象存储、Ingress 与密钥绑定；
- 初期可使用经过加固的 Compose，正式生产以 Kubernetes/Helm 为目标；
- CI：依赖安装、类型检查、单元测试、接口测试、镜像构建、依赖/镜像扫描；
- CD：部署 staging、执行 E2E、人工批准生产、灰度、健康检查、自动/人工回滚。

### 7.2 测试要求

| 层级 | 最低覆盖 |
|---|---|
| 单元测试 | 状态机、幂等回调、签名校验、权限、模板缺失、算法降级 |
| 集成测试 | MySQL、Redis、私有对象存储、上传确认、任务投递、回调写入 |
| 契约测试 | 小程序/管理端与主服务 DTO |
| E2E | 正常完成、质量不足、分析失败、重复回调、人工复核、反馈回复通知 |
| 安全测试 | 越权、伪造回调、弱口令、恶意上传、签名 URL 过期与审计 |

### 7.3 拒绝发布条件

以下任一项出现即阻断生产发布：

- 核心 E2E 路径失败；
- 高危或严重安全漏洞未关闭；
- 检测到 mock、默认 token、HTTP 外部入口或公共患者资产；
- 数据库迁移无备份与恢复验证；
- 关键监控、告警或审计未配置；
- 模板、阈值、算法版本或专家审核状态不可追溯；
- 合规、知情同意或临床验证责任边界未确认。

## 8. 分期里程碑和验收

| 阶段 | 目标 | 主要产出 | 阶段出口 |
|---|---|---|---|
| M0 安全封锁 | 清除开发默认风险 | 生产配置校验、账号治理、强密钥、私有资产访问 | 无 mock/default/自动建号/公开患者资产 |
| M1 可靠主链路 | 每条视频都有可恢复最终状态 | 状态机、analysis run、outbox、重试、死信、补偿 | 重复/迟到回调不影响最终报告 |
| M2 算法安全输出 | 不可靠时不误导患者 | 质量门控、降级、模板治理、人工复核 | 低质量和缺失模板不出确定等级 |
| M3 云上可运维 | 稳定运行、可恢复 | 容器化、私网、HTTPS、日志、监控、备份恢复 | 故障演练和恢复演练通过 |
| M4 可验证发布 | 发布可控、质量可量化 | CI/CD、测试金字塔、镜像扫描、灰度回滚 | 发布闸门自动执行且可审计 |
| M5 合规与临床准入 | 决定真实患者开放范围 | 授权、数据治理、专家验证、法规评估 | 责任人签字/审批完成 |

---

## 9. 首批实施顺序

1. 整改账号登录、Mock 禁用和生产配置硬校验；
2. 关闭本地静态患者资产暴露，建立鉴权签名访问；
3. 引入分析运行记录、终态保护、回调幂等与可靠投递；
4. 将模板缺失、低置信度和质量不足纳入统一降级状态；
5. 添加核心单元/集成/E2E 测试和生产镜像构建；
6. 建设云上 staging 与生产基础设施、监控、告警、备份；
7. 完成专家验证、临床/合规审核和灰度发布演练。

---

## 10. 规划自检

- 本规划未把医疗器械、临床验证或个人信息合规误写为仅靠代码可完成事项；
- 安全、可靠性、算法降级、云交付和运营治理均有独立验收出口；
- 正式生产目标与当前小规模受控内测目标相比显著扩大，已通过里程碑控制范围；
- 所有患者可见确定性评价均以质量门控、模板可用性与人工复核能力为前提；
- 本规划不允许以“页面已完成”替代“真实生产可用”。
