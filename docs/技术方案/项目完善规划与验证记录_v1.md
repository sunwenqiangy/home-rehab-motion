## 1. 目标与原则

本规划用于把当前项目实现与最新设计稿（患者端 V4、管理端 V2）对齐，并建立“执行-验证-记录”闭环，保障后续每次迭代可追溯。

执行原则：

1. 先对齐信息架构，再补齐页面能力，再统一后端契约。
2. 先补共享契约（`packages/shared-contracts`），再改服务，再改前端消费。
3. 保持患者端“适老化唯一版”原则，不再分裂业务流。
4. 每个里程碑都必须有验证记录，未记录视为未完成。

## 2. 当前基线与差距（2026-07-17审计）

### 2.1 患者端（miniapp）

现状能力（已具备）：

- 训练上传与分析轮询主链路：`training -> analyzing -> report` 已打通。
- 消息中心、反馈详情、历史记录已具备基础能力。
- 报告页已存在三阶段文案与反馈提交入口。

关键差距（相对 V4 设计稿）：

1. Tab 架构不一致：当前 `app.json` 为 5 Tab（含报告），设计稿为 4 Tab（首页/训练/历史/我的）。
2. 页面覆盖不足：缺 P03 指导详情、P04 上传确认分层、P10 反馈详情流程化展示、P11 全部徽章独立页的完整形态。
3. 首页信息架构不足：未实现“今日训练/反馈提醒/本周进展/阶段状态/最近训练”完整模块矩阵。
4. 适老化策略冲突：`mine` 页仍可切换标准模式，不符合“仅保留适老化展示策略”的评审结论。
5. 反馈表单能力不足：虽后端支持 `images` 字段，但前端尚未提供图片上传交互。

### 2.2 管理端（admin-web）

现状能力（已具备）：

- 已有 Dashboard、患者列表、视频列表+详情、反馈处理、指导内容编辑、阈值、模型版本、账号管理。
- 与 `main-service` 管理端 API 基本可联动。

关键差距（相对 V2 设计稿）：

1. 信息架构不完整：缺少路由化页面拆分（当前聚合在 `App.vue` 单页），与 M01-M12 页面边界不一致。
2. 页面编号映射偏差：当前菜单命名与设计稿 M 编号不完全一致（例如账号管理编号映射偏差）。
3. 缺 M04 患者详情、M09b 反馈详情页的独立沉淀与深链访问能力。
4. M08 多媒体资产管理能力不足：仅有基础字段编辑，缺步骤图/拍摄示意图/错误演示图（GIF）资产结构与预览。

### 2.3 服务端与契约层

现状能力（已具备）：

- `main-service` 已覆盖认证、训练、报告、通知、反馈、管理端核心 API。
- `analysis-service` 已有可运行分析模拟与阈值联动。
- `feedback` 状态流转（待处理/处理中/已回复/已关闭）已支持。

关键差距：

1. `shared-contracts` 字段偏薄：缺通知跳转语义、徽章/连续训练/stage-rule 配置等共享 DTO。
2. 报告阶段判断未参数化：前端按评分硬编码分阶段，不符合“后台参数化配置”的评审结论。
3. 指导内容结构不足：后端 `guidance` 模型未覆盖多媒体资产（步骤图、拍摄示意图、错误GIF）。
4. 历史/反馈/通知跨页面联动字段不全（例如统一 `relatedType`、`deepLink`、`bizStatusText`）。

## 3. 项目完善里程碑（建议 6 个迭代）

## 里程碑 M0：契约与设计基线冻结

范围：`packages/shared-contracts`、`docs`

交付：

- 新增统一 DTO：ReportStage、Badge、Streak、NotificationLink、GuidanceAsset。
- 输出页面-接口-状态词典对照表（患者端/管理端/后端统一口径）。

完成标准：

- 前后端引用同一枚举与类型。
- 新增契约可通过 TypeScript 编译。

## 里程碑 M1：患者端 IA 与导航重构（P01-P11 骨架）

范围：`apps/miniapp`

交付：

- Tab 改为 4 项（首页/训练/历史/我的）。
- 报告页由 Tab 改为业务详情页入口。
- 新增或重构页面骨架：P03/P04/P10/P11。
- 移除显示模式切换，仅保留适老化辅助设置。

完成标准：

- 页面路由矩阵与 `miniapp_v4_preview.html` 一致。
- 关键跳转链路可走通：首页 -> 训练 -> 上传 -> 分析 -> 报告 -> 反馈/历史。

## 里程碑 M2：患者端体验与闭环增强

范围：`apps/miniapp` + `services/main-service`

交付：

- 首页 8 区模块完整落位。
- 报告页三阶段动态展示改为后端下发（非前端硬编码）。
- 反馈表单支持图片上传（最多3张）。
- 消息中心支持类型化跳转与未读状态闭环。
- 新增徽章页（P11）与最近成就联动。

完成标准：

- 反馈“提交 -> 医护回复 -> 消息提醒 -> 反馈详情”闭环可验证。
- 徽章/连续训练数据在首页、报告、历史、我的四处语义一致。

## 里程碑 M3：管理端路由化与 M01-M12 对齐

范围：`apps/admin-web`

交付：

- 从单页聚合改为路由化页面拆分。
- 完整对齐页面：M01-M12（含 M09b）。
- M08 补齐多媒体资产编辑与患者端预览。

完成标准：

- 菜单、路由、页面编号与 `admin_v2_preview.html` 对齐。
- 关键操作可验证：反馈状态流转、指导内容编辑、阈值调整、模型版本查看。

## 里程碑 M4：主服务模型与 API 扩展

范围：`services/main-service`

交付：

- Guidance 结构扩展（多媒体资产字段）。
- 报告阶段策略配置化（可按阈值和连续达标次数计算）。
- 新增/补齐：患者详情、反馈筛选、通知深链字段、徽章与连续训练 API。

完成标准：

- API 契约与前端消费一致，无临时字段。
- 新接口可通过基础回归。

## 里程碑 M5：分析服务与质量策略完善

范围：`services/analysis-service`

交付：

- 置信度分层输出标准化（VQS/KCS/PRS 映射字段）。
- 质量不足原因结构化返回，支持前端精准提示。
- 与报告阶段计算的关键指标打通。

完成标准：

- 质量不足场景下可给出稳定、可解释的降级结果。
- 报告输出字段覆盖患者端和管理端展示需求。

## 里程碑 M6：联调验收与上线准备

范围：全仓

交付：

- 患者端、管理端、主服务、分析服务联调通过。
- 验收报告与遗留问题清单。

完成标准：

- 主链路和反馈闭环全部通过。
- 所有里程碑均有验证记录。

## 7. 风险与对策

1. 风险：前后端并行改造导致契约漂移。  
   对策：M0 先冻结共享契约，后续所有字段变更先改 `shared-contracts`。

2. 风险：患者端 IA 改造期间主链路回归。  
   对策：保留最小主链路回归用例（上传 -> 分析 -> 报告）为每日必测。

3. 风险：管理端拆页时功能分散、进度失控。  
   对策：按 M 页面编号拆分，先 P0 页面后 P1 页面，避免一次性大重构。

4. 风险：三阶段逻辑口径不统一。  
   对策：阶段判定只在服务端计算，前端只渲染后端下发结果。
