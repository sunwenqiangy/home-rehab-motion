# Home Rehab Motion · 二期能力规划与阶段判定优化方案

**版本**：V1.1  
**日期**：2026-08-20  
**适用范围**：主服务、分析服务、患者小程序、管理端  
**关联文档**：`动作分析评分与患者状态文案梳理_v1.md`、`激励机制完整方案_v1.md`

## 1. 文档结论

### 1.1 需要解决的不是“双轨”，而是“同名不同义”

当前 `ReportStage` 在两个位置被赋予了不同含义：

- 首页/训练摘要的 `stage`：代表患者的**康复旅程阶段**，由训练次数和康复周数决定；
- 报告页的 `stage`：代表患者的**本次动作表现**，由单次评分和等级决定。

两者都合理，但不应同名、同字段、同文案展示。否则会出现：首页显示“稳定练习”，报告页却显示“坚持成长”；一次评分波动还会让报告页阶段前进或回退。

### 1.2 推荐决策

采用“**一个旅程阶段 + 一份本次报告反馈**”模型：

1. `journeyStage` 是患者唯一可见的“阶段”，由累计训练与康复周数判定，仅用于首页、我的页、报告页的阶段卡片；
2. 本次报告不再计算第二个“阶段”，继续使用既有 `grade`、四维分、`improvementMessage`、`adviceSummary` 表达动作表现；
3. 如需在报告顶区给出一句“本次重点”，新增非阶段枚举 `reportFocus`，例如“先熟悉动作”“继续保持稳定”“保持当前节奏”；
4. `TrainingMotivationSnapshot` 用于**历史报告留档**，而不是让当前首页与历史报告强行显示完全相同的阶段。

> 这样既消除患者在同一页面语义下看到的矛盾，也保留“长期坚持”与“本次表现”两类必要反馈。

## 2. 当前实现与问题边界

### 2.1 当前两套判定

| 入口 | 实现位置 | 当前规则 | 实际语义 |
|---|---|---|---|
| 首页、训练摘要、激励快照 | `motivation.service.ts` 的 `resolveStage` | 康复第 1～2 周或训练少于 4 次：`corrective`；第 3～4 周或训练少于 8 次：`consolidation`；其余：`incentive` | 康复旅程/坚持程度 |
| 单次训练报告 | `report.service.ts` 的 `resolveReportStage` | 优秀或分数 ≥90：`incentive`；良好或分数 ≥75 且存在有效动作：`consolidation`；其余：`corrective` | 单次动作表现 |

现有枚举值及患者文案为：

| 值 | 患者端名称 |
|---|---|
| `corrective` | 熟悉动作 |
| `consolidation` | 稳定练习 |
| `incentive` | 坚持成长 |

### 2.2 问题示例

| 场景 | 首页阶段 | 报告页阶段 | 患者感受 |
|---|---|---|---|
| 训练 5 次、康复第 3 周，本次 92 分 | 稳定练习 | 坚持成长 | “我到底在哪个阶段？” |
| 已长期训练，本次视频质量待复核 | 坚持成长 | 熟悉动作（待复核时分数被置为 0） | “为什么练得越久又回到起点？” |
| 同一患者两次报告分数 91 → 73 | 坚持成长 | 坚持成长 → 熟悉动作 | 阶段像成绩，而不是康复过程 |

### 2.3 设计原则

1. **阶段不等于成绩**：阶段用于传达长期旅程，单次表现用评分和建议表达；
2. **长期体验只进不退**：患者可见旅程阶段默认只升级，不因一次视频质量或分数下降回退；
3. **待复核不下结论**：`review_required` 不输出动作评价，更不能借由“熟悉动作”暗示患者退步；
4. **报告留档可追溯**：历史报告显示分析完成当时的阶段快照；首页显示当前阶段，两者可因时间推进不同，但必须明确文案语义；
5. **坚持和质量解耦**：确认分析后记训练日；评分、趋势与质量类徽章仅在可信结果完成后产生。

## 3. 目标模型

### 3.1 字段与职责

| 字段 | 类型/取值 | 数据来源 | 适用位置 | 患者表达 |
|---|---|---|---|---|
| `journeyStage` | `corrective` / `consolidation` / `incentive` | 累计训练次数、康复周数、历史最高阶段 | 首页、我的页、报告阶段卡片 | 熟悉动作 / 稳定练习 / 坚持成长 |
| `grade` | 优秀 / 合格 / 需改进 / 无效 / 待复核 | 本次分析或人工复核 | 报告结果区 | 本次训练表现 |
| `reportFocus` | 非阶段提示枚举 | `grade`、有效次数、是否待复核、建议规则 | 报告顶区/阶段重点区 | 本次先关注什么 |
| `improvementMessage` | 文案 | 同动作的上一次已完成分析 | 报告页、首页摘要 | 与过去自己的变化 |
| `adviceSummary` | 可追溯建议数组 | 特征触发/人工复核 | 报告建议区 | 下一次怎样调整 |

### 3.2 `reportFocus` 建议定义

`reportFocus` 只描述本次训练重点，不能使用“阶段”“升级”“降级”等表达。

| 值 | 触发条件 | 患者标题 | 患者说明 |
|---|---|---|---|
| `review_pending` | `requiresManualReview=true` | 本次结果待复核 | 本次训练记录已收到，复核完成前暂不展示分数和动作判断。 |
| `retake_recommended` | `quality_insufficient` 或分析失败 | 建议重新拍摄 | 请按拍摄要求保证动作完整入镜、画面清晰稳定后重新上传。 |
| `learn_motion` | 无效、需改进或核心建议存在 | 本次先熟悉动作 | 跟着动作步骤慢慢完成，优先保证动作完整和舒适。 |
| `build_stability` | 合格或存在稳定性/保持时间提示 | 本次继续练稳定 | 保持节奏一致，逐步减少代偿并延长顶点保持。 |
| `maintain_rhythm` | 优秀且无高优先级建议 | 本次保持当前节奏 | 本次动作完成得不错，请按自己的节奏稳定练习。 |

### 3.3 阶段升级规则

现有规则是“周数或次数满足其一即可推进”，容易让训练极少但时间跨度长的用户进入高阶段。建议二期调整为**周数和训练次数均满足**，并引入历史最高阶段保护。

| 旅程阶段 | 建议进入条件 | 说明 |
|---|---|---|
| 熟悉动作 | 默认阶段 | 首次训练至基础训练期 |
| 稳定练习 | 康复第 3 周起 **且** 累计训练日 ≥4 | 既有时间沉淀，也有最低练习量 |
| 坚持成长 | 康复第 5 周起 **且** 累计训练日 ≥8 | 不因一次高分提前进入长期坚持阶段 |

推荐实现：

```text
computedJourneyStage = 根据康复周数 + 累计训练日计算
journeyStage = max(已记录的历史最高阶段, computedJourneyStage)
```

`max` 按 `corrective < consolidation < incentive` 比较。阶段回退不开放给自动规则；若存在临床或运营特殊需要，仅允许管理员留痕调整，并避免向患者展示“降级”字样。

## 4. 优化方案比较

| 方案 | 描述 | 优点 | 主要问题 | 结论 |
|---|---|---|---|---|
| A：仅统一为实时旅程阶段 | 删除报告评分阶段，报告实时读取当前 `motivation.stage` | 改动最少，首页与刚生成报告一致 | 打开旧报告时阶段会随当前训练变化，历史语境丢失 | 不建议单独采用 |
| B：保留两个同名阶段 | 首页按坚持、报告按评分继续使用 `stage` | 无需改 UI | 同名不同义的根因未解决 | 不采用 |
| C：旅程阶段 + 本次报告反馈 | 阶段唯一表示旅程；评分/建议表达本次表现 | 概念清晰、患者理解成本低、可持续扩展 | 需要调整 DTO 与前端展示 | **推荐** |
| D：旅程阶段 + 历史快照 | 在方案 C 上，报告留存分析完成时的旅程阶段 | 历史可追溯，避免旧报告被实时阶段覆盖 | 要处理旧数据回退 | **推荐落地形态** |

## 5. P2 能力规划

### P2-0：阶段语义收敛与数据治理（优先级 P0）

**目标**：先消除错误的阶段体验与字段歧义，不改变核心评分算法。

| 能力 | 交付内容 | 验收口径 |
|---|---|---|
| 阶段统一 | `ReportDto.stage` 改为旅程阶段；删除 `resolveReportStage` | 新生成报告与首页使用同一阶段定义 |
| 报告反馈拆分 | 新增 `reportFocus`；保留 `grade`、进步、建议 | 报告不再使用“阶段”表达本次得分 |
| 阶段快照 | 快照记录 `journey_stage`、版本、计算依据 | 历史报告能说明“分析完成当时处于什么阶段” |
| 旧数据兼容 | 无快照时按当前旅程阶段回退，并标记为历史回退值 | 旧报告可正常打开，不阻塞患者 |
| 规则治理 | 阶段阈值和阶段版本配置化，变更留审计 | 管理端可追溯谁在何时调整了规则 |

### P2-1：个体基线与相对进步（优先级 P1）

**目标**：在绝对模板评分基础上，让患者看见“相对自己”的变化。

| 能力 | 规则 |
|---|---|
| 个体动作基线 | 按“患者 × 动作”记录首次基线、滚动基线、样本数、版本与更新时间 |
| 基线样本门槛 | 少于 3 个高可信且非人工复核结果时，不展示基线趋势 |
| 相对变化 | 优先比较同动作的保持时间、稳定性、有效次数、综合分；保留当前既有优先级 |
| 异常保护 | 突变仅触发“建议关注拍摄/动作一致性”，不得自动推断病情变化 |
| 版本隔离 | 模板或核心算法版本变化后，趋势图标识版本边界，不直接拼接比较 |

> 个体基线是趋势与陪伴能力，不能替代金标准模板，也不能降低 `quality_insufficient` 和 `review_required` 的降级门槛。

### P2-2：长期趋势与阶段精细化（优先级 P1）

**目标**：将“是否坚持”和“是否练得更稳”分开展示，并减少偶然波动。

| 能力 | 规则 |
|---|---|
| 双趋势视图 | 坚持线：训练日/连续日；表现线：稳定性、保持时间、有效次数、综合分 |
| 滑动聚合 | 近 3～5 次高可信结果做中位数或滑动平均，不以单次结果判断长期趋势 |
| 阶段升级保护 | 使用“周数 AND 训练日 AND 历史最高阶段”规则，默认只升不降 |
| 周目标 | 保持“每天最多记 1 个训练日”，不将多次上传变成额外激励 |
| 管理观察 | 展示阶段分布、升级转化、质量不足率、待复核率和报告完成率 |

### P2-3：拍摄预检与异步反馈闭环（优先级 P1）

**目标**：降低无效上传和长时间等待的不确定感，保持“上传后进入分析页”的既有 UX 设计。

| 能力 | 规则 |
|---|---|
| 上传前预检 | 轻量抽帧检测清晰度、入镜、亮度、关键躯干点可见性；只提示重拍建议，不在端侧评分 |
| 分析页续航 | 任务排队时允许返回首页；下次进入从服务端状态恢复，不强制常驻等待 |
| 完成提醒 | 优先使用订阅消息；未授权时使用站内通知，且以 `videoId` 去重 |
| 延迟说明 | 超过预估等待时间时提示“视频已保存，可稍后在训练记录查看”，不诱导重复上传 |
| 质量不足引导 | 返回具体、可执行的拍摄原因，不归因于患者“练错” |

### P2-4：模板治理与研究支持（优先级 P2）

**目标**：让模板、阈值和数据导出可追溯，为后续算法升级提供证据。

| 能力 | 规则 |
|---|---|
| 模板版本评估 | 比较特征分布、阈值差异、受影响样本数、质量不足/待复核变化 |
| 灰度策略 | 按患者稳定分桶灰度；模板版本与阈值快照写入每份报告 |
| 回滚机制 | 版本启用前保留上一个可用版本；异常指标超过阈值自动告警、人工回滚 |
| 脱敏导出 | 最小化字段、权限审批、操作审计；默认不导出原视频 |
| 算法评测集 | 按动作、光照、机位、难度分层，人工标注与算法结果并列评估 |

## 6. 数据与接口改造建议

### 6.1 共享类型

```ts
export type JourneyStage = 'corrective' | 'consolidation' | 'incentive';

export type ReportFocus =
  | 'review_pending'
  | 'retake_recommended'
  | 'learn_motion'
  | 'build_stability'
  | 'maintain_rhythm';
```

迁移期可保留 `ReportStage` 作为 `JourneyStage` 的类型别名，避免一次性扩大前后端改动面；完成迁移后逐步替换命名。

### 6.2 报告 DTO

```ts
interface ReportDto {
  // 既有字段省略
  journeyStage: JourneyStage;
  journeyStageSource: 'snapshot' | 'current_fallback';
  reportFocus?: ReportFocus;
  reportFocusText?: string;
}
```

迁移期建议同时返回旧 `stage`，其值等于 `journeyStage`，并在前端切换完成后删除旧字段。**不得再返回由单次评分推导的 `stage`。**

### 6.3 快照建议

当前 `TrainingMotivationSnapshot` 已有 `stage` 字段。P2-0 可先不建新表：

1. 将既有字段的业务语义明确为“分析完成时的 `journeyStage`”；
2. 增加 `stage_rule_version` 和 `stage_basis`（康复周数、累计训练日），便于解释与审计；
3. 报告读取快照时，只有该视频快照存在且语义版本有效才使用；否则回退到当前 `journeyStage`；
4. 首页始终展示当前 `journeyStage`，历史报告展示快照阶段时，标题应为“本次训练时的阶段”，避免与首页当前阶段混淆。

- 不修改分析服务的四维评分权重、阈值或模板；
- 不将评分结果直接作为阶段升级条件；
- 不在患者端加入排行榜、冲刺任务或连续记录中断惩罚；
- 不因一次 `quality_insufficient`、`failed` 或 `review_required` 回滚训练日和旅程阶段。

## 8. 验收标准

### 8.1 阶段与报告

1. 新生成报告的 `journeyStage` 与首页当前阶段使用同一套计算规则；
2. 报告页不再存在“由单次 90 分跳到坚持成长、下一次低分回到熟悉动作”的现象；
3. `review_required` 报告显示“本次结果待复核”，不以 `corrective` 替代阶段；
4. 历史报告存在快照时展示“本次训练时的阶段”；首页展示“当前阶段”，两者因时间推进不同属于正常且文案可解释；
5. 每条建议仍可追溯到算法特征或人工复核结果。

### 8.2 数据与安全

1. 同一自然日最多记录 1 个训练日；
2. 质量不足、失败、待复核均不回滚已确认的训练记录；
3. 样本不足时不展示个体基线趋势；
4. 模板、阈值、算法和阶段规则版本均可追溯；
5. 阶段规则、模板版本变更有审计记录，旧报告保留当时快照。
