# 缩腹运动闭环切分与患者个体化评价优化方案

> 状态：方案待落地  
> 适用范围：`abdominal_crunch`（缩腹运动）  
> 核心目标：让系统按完整动作周期稳定计数，并在患者场景中做到“安全严格、完成包容、进步可见”。

---

## 1. 背景与问题概述

当前缩腹运动的切分逻辑，主要依据肩中点到髋中点的三维向量相对竖直方向的夹角（以下称“**缩腹信号**”）寻找局部最高点，再把一个局部最高点近似视为一次缩腹动作。

这个方法实现简单，但它把“姿态信号的局部起伏”直接等价为“肉眼看到的一次完整抬腹”。两者并不总是一致：

- 回落过程中的轻微姿态反弹，可能形成局部最高点，被误计为一次动作；
- 真实动作如果幅度较小、深度估计波动大，或被平滑处理压低，可能无法形成足够明显的局部最高点，从而被漏计；
- 同一套绝对幅度规则若直接用于患者，可能把“小幅但完整、安全”的康复动作判得过低，影响患者信心和训练依从性。

因此，需要将问题拆开处理：

1. **切分问题**：这一段是否构成一个完整动作周期；
2. **评价问题**：该完整动作的质量如何，是否较患者自身近期水平进步；
3. **安全问题**：是否存在风险、明显代偿、视频质量不足或动作类型不匹配。

## 2. 当前实现与数据链路

### 2.1 当前缩腹信号

文件：`services/analysis-service/app/core/phase_segmenter.py`

缩腹信号由肩中点到髋中点的三维向量计算：

```python
angle = np.degrees(np.arctan2(np.hypot(dx, dz), abs(dy) + 1e-8))
```

它表达的是躯干相对竖直方向的三维屈曲角，不是画面中“腹部最高点”的直接像素高度。

### 2.2 当前切分规则

当前逻辑为：

1. 对缩腹信号平滑；
2. 使用 `scipy.signal.find_peaks` 寻找局部峰；
3. 缩腹默认最小峰距为 `3.5 × effective_sample_fps`；
4. 峰显著性（prominence）下限为：

```python
max(0.30, signal_std * 0.12, robust_range * 0.12)
```

5. 使用相邻峰的中点作为周期边界；
6. 周期时长要求在 `4s ~ 18s`。

现有逻辑的核心假设是：

```text
一个满足峰距与显著性条件的局部峰 = 一次完整缩腹动作
```

这正是当前误计与漏计的根源。

### 2.3 当前分析链路

```text
视频上传
  → MediaPipe 姿态提取
  → 按 MAX_ANALYSIS_FRAMES 限制实际抽帧

```

## 3. 已确认的样本问题与数据

### 3.1 样本运行条件

当前验证使用护士专门录制的标准缩腹视频。该视频动作幅度较大，适合作为算法标注与回归验证样本，但不能直接作为患者绝对幅度的硬门槛。

本地分析日志对应样本（`video_id=343/344`）的主要运行数据：

| 项目 | 数值 |
|---|---:|
| 源视频帧率 | 30 fps |
| 源视频总帧数 | 3426 帧 |
| 视频时长 | 约 114 秒 |
| `MAX_ANALYSIS_FRAMES` | 600 帧 |
| 抽帧步长 | 6 帧 |
| 实际抽帧率 `effective_sample_fps` | 5 fps |
| 姿态帧数 | 571 帧 |
| 当前正式切分结果 | 10 次 |
| 当前峰最小间隔 | 17 帧（约 3.5 秒） |
| 当前峰显著性下限 | 0.30° |

> 注意：所有动作时长、最小间隔与稳定时间必须以 `effective_sample_fps` 换算；不能只使用配置中的 `SAMPLE_FPS=10`，因为长视频会受帧预算影响被自动降采样。

### 3.2 前段问题：一个周期被拆为第 3、4 段

当前算法的第 3、4 段：

| 当前段 | 时间范围 | 当前峰时间 | 峰显著性 |
|---|---:|---:|---:|
| 第 3 段 | 19.0s ~ 27.2s | 22.6s | 0.760° |
| 第 4 段 | 27.2s ~ 36.0s | 32.0s | 0.334° |

信号观察：

- 22.6s 对应一次明显收缩顶点；
- 32.0s 的候选峰仅略高于 `0.30°` 的最低显著性阈值；
- 32.0s 后的回落幅度约为 `0.33°`，明显弱于完整动作的典型起伏；
- 人工观看视频认为第 3、4 段属于同一个完整动作周期。

结论：第 4 段更符合“回落过程中的局部反弹”，而不是独立的“收缩 → 回落 → 稳定”闭环。

### 3.3 后段问题：真实 3 个周期仅识别为第 9、10 段

人工观看视频确认的后段节奏如下：

| 实际周期 | 腹部抬高顶点 | 回落平稳 |
|---|---:|---:|
| 第 1 次 | 约 83s | 约 89 ~ 90s |
| 第 2 次 | 约 95s | 约 100s |
| 第 3 次 | 约 107s | 约 112s |

> “107s 腹部抬到最高，102s 回落平稳”应为时间顺序笔误；按视频节奏应为约 `112s` 回落平稳。

当前算法结果：

| 当前段 | 时间范围 | 当前识别峰 |
|---|---:|---:|
| 第 9 段 | 81.0s ~ 96.0s | 85.0s |
| 第 10 段 | 96.0s ~ 114.0s | 107.6s |

候选信号数据：

| 候选位置 | 时间 | 峰显著性 | 当前处理 |
|---|---:|---:|---|
| 候选峰 1 | 85.0s | 0.312° | 被识别 |
| 候选峰 2 | 100.0s | 0.258° | 低于 0.30°，被过滤 |
| 候选峰 3 | 107.6s | 0.349° | 被识别 |
| 尾部局部峰 | 112.2s | 无完整后续回落可计算 | 未作为独立周期 |

结论：中间真实动作在三维肩髋角信号上未达到固定显著性门槛，而视频尾部动作又受“必须有后续谷值/回落证据”的限制，导致多个动作被合并。

### 3.4 为什么总数“刚好 10 次”不能证明正确

人工观察说明：

- 前段第 3、4 段实际应合并：当前结果多算 `+1`；
- 后段第 9、10 段实际应拆成 3 次：当前结果少算 `-1`；

因此当前结果 10 次可能只是误差抵消：

\[
\text{真实次数} + 1 - 1 = 10
\]

不能仅以总次数恰好相同来判断算法正确，必须验证每个周期的边界与动作语义。

## 4. 根因分析

### 4.1 算法信号不等于肉眼腹部高度

当前“峰”指的是三维肩髋屈曲角的局部最大值，并非肉眼看到腹部最高的画面帧。

```text
视频观察：腹部抬高 → 回落 → 平稳
当前算法：三维肩髋夹角是否形成足够明显的局部峰
```

受以下因素影响，两者会不一致：

- MediaPipe 深度 `z` 为单目估计的代理值，存在波动；
- 护士或患者的身体比例、衣物、镜头距离、侧身角度不同；
- 肩、髋关键点在遮挡或轻微转身时可能偏移；
- Savitzky-Golay 与移动平均平滑会压低窄峰或小幅动作；
- 固定 prominence 门槛会同时面临“回弹误检”和“小动作漏检”的矛盾；
- 视频末尾缺少未来帧时，传统峰显著性难以确认最后一个动作。

### 4.2 固定全局阈值无法同时解决多算与漏算

对当前样本：

| 调整方式 | 可能改善 | 同时带来的风险 |
|---|---|---|
| 提高 prominence | 过滤 32s 回弹峰 | 95s 的真实小动作更难识别 |
| 降低 prominence | 找回 100s 附近候选动作 | 回弹、噪声、姿态抖动会被更多计数 |
| 只增大最小峰距 | 合并过近回弹 | 会漏掉患者节奏较快但真实的完整动作 |
| 只按谷-峰-谷 | 抑制部分抖动 | 回位谷浅时容易把多个真实动作合并 |

因此，不能仅修改一个 `prominence` 常数。

### 4.3 评分与切分当前耦合过紧

当前总分依赖每个 Rep 的特征比对。若切分错误：

- 一个真实动作被拆成两段，幅度、保持时长和速度均会被扭曲；
- 三个动作被合并成两段，视频级平均也会失真；
- 错误 Rep 会进入患者历史趋势，后续个人基线可能被污染。

所以必须先稳定切分，再建立患者个人基线和患者友好评分。

## 5. 设计原则

### 5.1 三层评价，不用一个总分承担全部意义

| 层级 | 要回答的问题 | 基本原则 |
|---|---|---|
| 完成度 | 是否完成了完整、安全的动作；完成几次 | 对动作结构严格，对幅度包容 |
| 动作质量 | 控制、节奏、保持、代偿做得如何 | 参考个人基线与阶段目标 |
| 安全状态 | 是否有风险、明显代偿、视频不可靠 | 严格；必要时进入人工复核 |

### 5.2 标准护士视频的正确定位

护士标准视频用于：

- 定义动作方向；
- 定义完整动作节奏；
- 定义高质量动作的控制与保持特征；
- 定义安全风险与明显错误代偿的边界；
- 作为算法标注和回归测试样本。

护士标准视频**不应**作为所有患者“必须达到同样绝对幅度”的硬门槛。

### 5.3 患者小幅动作的判定原则

患者因术后阶段、疼痛、体型、柔韧性、疲劳等原因，动作幅度不同。系统应遵循：

```text
小幅 + 有连续收缩 + 有回落 + 有稳定 + 无安全风险
= 计为一次完整有效训练
```

不应因为未达到护士幅度就直接判为无效。

但以下情况仍应严格处理：

- 动作类型明显不匹配；
- 纯姿态抖动、无连续收缩与回落；
- 明显风险或代偿；
- 视频质量或姿态置信度不足；
- 关键点长期缺失。

## 6. 目标方案：缩腹完整闭环状态机

### 6.1 从“找峰”升级为“识别完整动作”

目标语义：

```text
稳定准备
  → 连续收缩 / 抬腹
  → 顶点
  → 连续回落
  → 回落后稳定
  = 一个完整缩腹周期
```

### 6.2 状态定义

| 状态 | 含义 | 关键证据 |
|---|---|---|
| `REST` | 准备或回落后的稳定状态 | 角速度低且持续一定时间 |
| `CONTRACTING` | 正在抬腹/收缩 | 连续同方向变化，累计变化超过噪声门槛 |
| `PEAK` | 动作顶点 | 局部最大值，速度减小或改变方向 |
| `RETURNING` | 正在回落 | 峰后出现反方向连续变化 |
| `STABLE_AFTER_RETURN` | 回落后稳定 | 回落后低速度持续一定时间 |
| `COMPLETE` | 完整周期 | 完成完整闭环，输出 Rep |
| `REBOUND` | 回落中的局部反弹 | 前一次动作尚未稳定，且独立幅度不足 |
| `INCOMPLETE_TAIL` | 视频尾部候选动作 | 已有收缩与足够回落，但稳定窗口被视频结束截断 |

### 6.3 切分规则

#### 规则 A：计为完整周期

候选动作需满足：

1. 存在连续收缩；
2. 出现本周期顶点；
3. 顶点后有连续回落；
4. 回落后出现短暂稳定；
5. 周期时长处于合理范围；
6. 累计变化大于噪声门槛。

#### 规则 B：回弹不单独计数

若候选局部峰出现时：

- 前一周期仍处于 `RETURNING`，尚未完成回落稳定；
- 候选峰相对局部基线变化很小；
- 峰后没有独立、完整的回落稳定闭环；

则标记为 `REBOUND`，并合并到当前周期，不新增 Rep。

这将解决当前样本中第 3、4 段的误拆问题。

#### 规则 C：低幅但完整的患者动作可计数

不能以护士绝对幅度判定。采用“噪声门槛 + 相对幅度”规则：

\[
A_{candidate} \ge \max(A_{noise}, r \times A_{reference})
\]

其中：

- \(A_{noise}\)：姿态估计噪声下限，仅用于排除抖动；
- \(A_{reference}\)：优先为患者个人近期有效动作的幅度中位数；冷启动时取当前视频候选动作幅度中位数；
- \(r\)：允许小幅但真实动作被识别的比例因子。

#### 规则 D：视频尾部动作

最后一个动作不能强制要求存在完整的“未来稳定窗口”。如果已经满足：

- 有明确连续收缩；
- 有动作顶点；
- 峰后已有足够比例的回落；
- 时长合理；

可标记为 `INCOMPLETE_TAIL` 并按规则计入完成次数，同时记录较低的切分置信度。

这将解决 107s 顶点、约 112s 回落的尾部动作漏计风险。

### 6.4 初始配置建议

以下值应作为可版本化配置的初值，必须经过标注集校准后才能定版：

```python
ABDOMINAL_SEGMENT_CONFIG = {
    "min_stable_seconds": 0.6,
    "min_contraction_seconds": 0.8,
    "min_return_seconds": 0.8,
    "min_cycle_seconds": 3.5,
    "max_cycle_seconds": 18.0,
    "noise_floor_deg": 0.20,
    "candidate_relative_amplitude_ratio": 0.30,
    "rebound_relative_amplitude_ratio": 0.20,
    "tail_min_return_ratio": 0.45,
}
```

所有时间单位必须依据 `effective_sample_fps` 转为帧数。

## 7. 患者个体化评价方案

### 7.1 个人基线建立

为每位患者、每个动作类型分别建立基线：

```text
user_id + action_type = 一套独立个人基线
```

建议新增 `PatientActionBaseline`，保存：

- 有效样本视频数；
- 有效 Rep 数；
- 缩腹幅度中位数、P25、P75；
- 控制指标中位数；
- 顶点保持时长中位数；
- 基线版本；
- 来源视频 ID；
- 基线状态：`warming_up` / `provisional` / `stable`。

### 7.2 冷启动策略

患者前 3 个高置信有效视频，或累计不足 8 个完整安全周期时：

- 不以个人幅度不足做负向扣分；
- 仍识别完成次数、安全风险与明显代偿；
- 患者端使用“系统正在了解您的动作节奏”的文案；
- 不直接将护士幅度作为患者失败门槛。

### 7.3 基线生效与更新

基线生效建议满足以下任一条件：

```text
至少 3 个高置信有效视频
或
至少 8 个完整、安全的有效周期
```

更新规则：

- 仅使用高置信、非人工复核、无明显安全风险的训练；
- 取最近 5 个视频、最多 30 个有效 Rep；
- 使用中位数和分位数，避免偶发疲劳/拍摄异常污染；
- 单次更新限制最大变化幅度，避免低幅训练持续把基线拉低；
- 标准动作与患者动作对比应保留，但只用于质量提示与理想目标，不用于否定小幅完整训练。

### 7.4 评分表达

建议内部保留总分用于趋势和后台，但患者端优先展示：

| 内容 | 示例 |
|---|---|
| 完成度 | “已完成 8 次完整动作” |
| 控制质量 | “回落较平稳” |
| 个人趋势 | “与近期训练相比保持稳定” |
| 下一步建议 | “抬高后停留约 1 秒，不需要刻意增加幅度” |
| 安全提示 | “检测到颈肩代偿，请适当减小抬高幅度并放松肩部” |

避免优先展示：

```text
动作评分：52 分，幅度不足。
```

## 8. 数据模型与接口改造建议

### 8.1 视频级分析结果增加切分溯源

建议在 `VideoEvaluationResult` 增加：

```prisma
segmentation_version  String? @db.VarChar(64)
segmentation_snapshot Json?
personal_baseline_version String? @db.VarChar(64)
personalization_snapshot  Json?
completion_summary        Json?
```

字段说明：

| 字段 | 用途 |
|---|---|
| `segmentation_version` | 实际使用的切分算法版本 |
| `segmentation_snapshot` | 正式周期、回弹候选、尾部候选、新旧算法差异与理由 |
| `personal_baseline_version` | 本次评价使用的患者基线版本 |
| `personalization_snapshot` | 基线来源、当前值与相对表现，保证历史报告可重现 |
| `completion_summary` | 完成度、安全状态、患者友好文案所需摘要 |

### 8.2 建议新增患者基线表

## 9. 分阶段落地计划

### 阶段 P0：固化样本、实现闭环切分、Shadow 对照

#### 目标

先解决“次数与边界是否正确”，不立即影响患者正式分数。

#### 工作项

1. 固化当前护士标准视频的脱敏关键点 JSON 与人工周期标注；
2. 新增缩腹状态机切分 `cycle_state_machine`；
3. 保留旧 `legacy_peak` 逻辑；
4. 新增运行模式：

```text
legacy_peak
shadow
cycle_state_machine
```

5. `shadow` 模式下：旧算法生成正式结果，新算法仅写入对比诊断；
6. 保存新旧切分计数、边界、回弹和尾部候选理由；
7. 保证预览/回填使用相同的预处理、实际 fps 与切分版本。

#### 推荐文件

| 文件 | 改动 |
|---|---|
| `services/analysis-service/app/core/phase_segmenter.py` | 新增缩腹状态机，不删除旧逻辑 |
| `services/analysis-service/app/core/models.py` | 增加候选周期诊断结构 |
| `services/analysis-service/app/core/constants.py` | 增加版本化切分参数 |
| `services/analysis-service/app/core/config.py` | 增加模式开关 |
| `services/analysis-service/app/tasks/analyze_video.py` | 双跑、保存切分诊断与版本 |
| `services/analysis-service/app/api/analysis.py` | 预览回填遵循正式分析上下文 |
| `services/main-service/prisma/schema.prisma` | 增加 `segmentation_version/snapshot` |

#### 验收标准

- 当前护士样本：第 3、4 段合并为一个完整周期；
- 当前护士样本：83s、95s、107s 三次动作均能识别；
- 每个正式周期可输出开始、顶点、回落、稳定的诊断证据；
- 被合并的局部反弹可在诊断中看到 `REBOUND` 与理由；
- 长视频、短视频在不同 `effective_sample_fps` 下使用相同时间语义；
- `shadow` 不影响患者正式结果；
- 无法可靠判断的低置信视频仍进入 `review_required`。

### 阶段 P1：标注集验证与正式切换

#### 目标

基于样本数据验证新算法优于旧算法后，才让状态机结果成为正式计数。

#### 工作项

1. 收集至少：
   - 20 个标准/教学样本；
   - 30 个脱敏患者样本；
   - 所有新旧计数不一致样本均人工复核；
2. 建立测试指标：
   - 周期计数绝对误差（MAE）；
   - 周期级 Precision / Recall；
   - 顶点时间误差；
   - 边界时间误差；
   - 回弹误计率；
   - 小幅完整动作召回率；
3. 达标后将生产模式切换到 `cycle_state_machine`；
4. 保留配置级回滚到 `legacy_peak` 的能力。

#### 推荐切换门槛

- 新算法周期计数 MAE 优于旧算法；
- 当前护士样本完全符合人工标注；
- 患者小幅完整动作召回率不下降；
- 新增误计率不高于旧算法；
- 差异样本均有可解释诊断；
- 不影响骨盆倾斜、膝关节旋转现有生产结果。

### 阶段 P2：患者个人基线与患者报告升级

#### 目标

在切分稳定后，让评价更符合患者实际能力，提升训练依从性。

#### 工作项

1. 新增 `PatientActionBaseline`；
2. 实现冷启动、基线建立、滑动更新与版本快照；
3. 将“完整但小幅”从 `invalid` 中分离；
4. 报告 DTO 增加完成度、质量、个人进步与安全状态；
5. 小程序报告页降低总分视觉优先级，突出完成、进步与建议；
6. 后台展示患者基线、切分证据和新旧算法差异。

#### 验收标准

- 无训练历史的患者不会因小幅完整动作直接被护士模板判为无效；
- 建立个人基线后可展示与近期自身水平的关系；
- 单次疲劳或低幅结果不会明显拉低基线；
- 不同动作之间个人基线隔离；
- `review_required`、人工审核优先级、既有安全提示不受影响；
- 历史结果可按当时模板、阈值、切分版本和基线快照追溯。

## 10. 测试方案

### 10.1 单元测试

新增 Python 测试，至少覆盖：

1. 回落中的局部反弹不单独计为 Rep；
2. 显著性较低但具备“收缩 → 回落 → 稳定”的动作仍可被识别；
3. 尾部动作已完成收缩与足够回落时可按尾部规则计数；
4. 纯噪声与过短抖动不计数；
5. 低幅完整动作可识别，但纯噪声不被放宽；
6. 3fps、5fps、10fps 的同一时间语义下周期数一致；
7. 旧峰值逻辑保留回归测试，确保可回滚；
8. 患者基线冷启动、更新、异常样本排除与动作隔离。

### 10.2 集成测试

- 重新分析同一视频后，旧 Rep 评分与特征记录可正确清理并重写；
- 切分诊断、模板版本、基线版本均被持久化；
- 回调到 main-service 后报告 DTO 正常生成；
- 小程序在新字段缺失、`warming_up`、个体化、人工复核四种状态下均可展示；
- 管理端可查看切分证据与算法版本。

### 10.3 人工验收

由护士/治疗师对标注视频确认：

- 每次动作开始、顶点、回落稳定的位置；
- 哪些候选是回弹，哪些是真实动作；
- 小幅患者动作在临床上是否应计为完成；
- 安全文案、建议文案是否恰当、不会制造焦虑。

## 11. 风险与控制措施

| 风险 | 影响 | 控制措施 |
|---|---|---|
| 状态机阈值偏严 | 漏掉患者小幅完整动作 | 用相对幅度、个人基线与标注集校准 |
| 状态机阈值偏松 | 回弹/噪声多算 | 必须要求收缩—回落—稳定闭环 |
| 视频尾部误判 | 最后一个动作被多算或漏算 | 单独 `INCOMPLETE_TAIL` 规则与较低置信度 |
| 切分变更影响历史趋势 | 报告前后不可比 | 记录切分版本；必要时管理员重分析补齐 |
| 护士模板压低患者分数 | 打击患者依从性 | 完成度与质量分离，引入个人基线 |
| 个人基线被疲劳样本拉低 | 评价失真 | 高置信筛选、滑动窗口、中位数/分位数、单次更新上限 |
| 新算法直接上线风险高 | 患者端计数波动 | 先 `shadow`，人工抽检差异样本，再灰度切换 |

---

## 12. 最终决策建议

1. **不建议**只调高或调低当前峰显著性阈值；
2. **优先实施**缩腹完整闭环状态机，并先运行 `shadow` 模式；
3. 当前护士标准视频应作为首个严格回归样本，而不是患者绝对幅度门槛；
4. 切分稳定后再引入个人基线，防止错误周期污染患者历史；
5. 患者端优先展示“完成次数 + 安全状态 + 个人进步 + 一条可执行建议”，总分降为次级信息；
6. 对安全风险、动作类型错误、视频质量不足保持严格，并继续使用人工复核兜底。

核心原则：

> **对动作结构和安全严格，对患者幅度与进步包容；先把周期数对，再谈个体化评分。**

## 13. 实施时序、资源约束与切换条件

### 13.1 当前只有一条标准视频时如何验证

当前护士标准视频可以作为第一条“黄金标注样本”，但不能作为患者泛化能力的证明。

应由护士/治疗师为该视频标注每个动作的：

| 标注字段 | 含义 |
|---|---|
| `start` | 开始收缩/抬腹的时间 |
| `peak` | 腹部抬高的顶点时间 |
| `return_end` | 基本回落完成的时间 |
| `stable_end` | 回落后重新稳定的时间 |
| `type` | `complete` / `rebound` / `tail_complete` |

最小回归要求：

- 原第 3、4 段对应区域标为 1 个 `complete`，中间小波动标为 `rebound`；
- 83s、95s、107s 三处均为独立完整动作；
- 对同一时间序列以 3fps、5fps、10fps 运行时，结果保持相同时间语义；
- 多次执行结果稳定一致。

这一阶段只能得出：

> 新规则解决了当前标准视频已确认的误拆与漏拆问题。

不能得出“算法已适用于所有患者”的结论。

### 13.2 P0、P1、P2 的启动时机

| 阶段 | 何时开始 | 核心产出 | 是否影响患者正式结果 |
|---|---|---|---|
| P0 | 立即开始 | 闭环切分、新旧对照、诊断数据、标准视频回归 | 否 |
| P1 | P0 标准视频通过后进入 Shadow 观察 | 患者差异样本审核、逐步切换正式计数 | 初期否；灰度后逐步是 |
| P2-A | P1 新切分稳定运行后 | 个人基线表、冷启动、基线快照、后台纠错 | 否 |
| P2-B | P2-A 基线数据可靠后 | 患者报告“完成+质量+进步+安全”升级 | 是，展示层升级 |

#### P1 进入条件

P0 完成后立即运行 Shadow。建议满足以下条件再从 Shadow 进入正式灰度：

1. 当前护士标准视频完全通过人工标注；
2. 累积至少 10 条高置信患者视频；
3. 若新旧计数存在差异，至少积累 5 条差异样本；样本不足则继续 Shadow；
4. 护士/治疗师抽查所有新旧计数差异样本；
5. 不存在未解释的严重误计数；
6. 可通过配置即时回滚到旧算法。

建议 Shadow 至少运行 1～2 周或一个自然训练周期，取“时间窗口”和“样本量”中更晚满足的条件。

#### P1 灰度方式

```text
内部/管理员重分析
  → 高置信、拍摄合格的患者视频
  → 5% 灰度
  → 20% 灰度
  → 全量启用
```

业务量较小时，可以不按百分比，而按人工审核通过的视频类别逐步扩大范围。

#### P2 启动条件

P2 依赖动作周期、幅度、保持时长等 Rep 级数据，因此必须在 P1 新切分稳定后开始。建议条件：

- 新切分已经正式启用并稳定运行至少 1～2 周；
- 没有因计数问题发生重大回滚；
- 已出现部分连续训练患者，可用于验证 3 次以上训练的基线建立；
- 护士/治疗师确认患者文案和安全规则。

### 13.3 首次上传、个人基线与人工纠错

个人基线不是患者第一次上传的绝对标准，而是：

> 在视频可靠、动作完整、安全可接受的前提下，患者近期多次训练的稳定能力范围。

基线状态：

| 状态 | 条件 | 本次报告策略 |
|---|---|---|
| `warming_up` | 少于 3 个高质量视频且少于 8 个完整安全周期 | 评估完成、质量、安全；不做个人幅度趋势评价 |
| `provisional` | 至少 3 个高质量视频或至少 8 个完整安全周期 | 形成临时基线，趋势提示保守 |
| `stable` | 建议至少 5 个高质量视频或 20 个有效周期 | 正式显示个人趋势和阶段性进步 |

第一次上传仍应评估：

1. 视频是否可靠；
2. 是否完成完整动作周期；
3. 是否存在明显代偿或安全风险；
4. 与护士标准的方向、节奏、控制差异。

第一次上传不应评估“是否达到患者个人历史水平”，因为尚无历史；护士幅度也不能直接作为失败线。

#### 哪些数据可以进入基线

仅纳入同时满足以下条件的 Rep：

```text
视频质量 passed
姿态/分析置信度 high
完整闭环 complete 或符合尾部规则的 tail_complete
安全状态 safe
未人工判定为错误动作
无明显代偿
```

#### 如何防止基线被一次疲劳或异常视频拉低

- 取最近 5 个高质量视频、最多 30 个有效周期；
- 使用中位数、P25、P75，不使用最近一次或简单平均；
- 单次更新限制最大变化幅度为 10%～15%；
- 低置信、代偿、疼痛反馈、拍摄不合格、人工复核的视频不更新基线；
- 连续低幅表现只标记为“当前状态下降”，不能自动重写长期能力基线；必要时由治疗师调整阶段目标或重建基线。

#### 后台人工纠错能力

后台应支持：

- 排除指定视频/Rep，不纳入基线；
- 修正动作次数和周期边界；
- 标记回弹、漏检、尾部动作；
- 覆盖安全状态；
- 重建、冻结或恢复患者基线；
- 设置患者康复阶段目标；
- 记录谁、何时、因何原因做了修改，以及修改前后值。

人工修正结果优先于算法输出。

### 13.4 2C2G 服务器的 Shadow 资源约束

当前生产分析 Worker 资源有限，Shadow 必须做到“**双切分，不双分析**”。

正确的 Shadow 流程：

```text
视频下载、解码                    运行 1 次
MediaPipe Pose 姿态提取           运行 1 次
DataPreprocessor 预处理           运行 1 次
  ├─ legacy_peak 旧切分           运行 1 次
  └─ cycle_state_machine 新切分   运行 1 次
旧切分的参数计算、模板比对、评分     运行 1 次（正式结果）
新切分的参数计算、模板比对、评分     不运行
患者报告与回调                     运行 1 次
```

禁止的做法：

```text
为新算法再次下载视频
再次解码/抽帧
再次运行 MediaPipe
再次执行完整预处理
再次执行完整特征计算、模板比对和评分
保存第二套完整特征表、Rep 评分表、视频评分表
```

这些做法会使 2C2G 单 Worker 的 CPU、内存、队列等待和任务超时风险接近翻倍，不允许在 P0 Shadow 中使用。

#### Shadow 只保存轻量诊断

建议将 Shadow 结果写入 `VideoEvaluationResult.segmentation_snapshot`，而非保存第二套完整评分：

```json
{
  "shadow": {
    "legacy_version": "abdominal_peak_v1",
    "legacy_rep_count": 10,
    "cycle_version": "abdominal_cycle_v2",
    "cycle_rep_count": 9,
    "count_delta": -1,
    "effective_sample_fps": 5.0,
    "accepted_cycles": [],
    "rejected_candidates": [],
    "timings_ms": {
      "legacy_segment": 0,
      "cycle_segment": 0,
      "shadow_overhead": 0
    }
  }
}
```

控制要求：

- 每个视频最多记录 50 个候选；
- 理由字段限制长度；
- 不复制已经保存的逐帧关键点 JSON；
- 诊断过大时仅保留摘要和前 N 个差异；
- 只对 `abdominal_crunch` 启用 Shadow；
- 视频质量不足、关键点不足、低置信、非缩腹动作时跳过 Shadow；
- 记录 `pose_extract_ms`、`preprocess_ms`、`legacy_segment_ms`、`cycle_segment_ms`、`shadow_total_overhead_ms`；
- 监控单任务耗时 P50/P95、Redis 队列等待、Worker CPU/内存、超时率与失败率；
- 必须保留配置级回退：`ABDOMINAL_SEGMENTATION_MODE=legacy_peak`。

结论：共享姿态提取和预处理、仅双跑切分时，新增成本相对 MediaPipe 很小，适合当前 2C2G；完整双分析不适合当前服务器。
