# Home Rehab Motion 正式生产整改实施计划

**依据**：`正式生产整改规划_v1.md`  
**执行状态**：进行中  
**执行策略**：按 M0 → M1 → M2 → M3/M4 → M5 顺序推进；每个阶段必须通过出口验证后再扩大范围。

## 本轮确认的产品与实施决策

1. **密钥轮换暂缓**：已识别生产密钥和模板 Secret 的治理风险；本轮不修改现有密钥或环境文件，后续由部署负责人统一轮换并清理历史暴露面。生产硬门禁、Mock 开关检查仍保留并继续执行。
2. **指导内容不引入草稿状态**：指导内容以“完整保存版本 + 启用/下线”管理。每次保存生成不可变历史版本；患者端只读取 `status=1` 的内容。`published_version` 在当前模型中表示“当前可启用版本”，不再表达独立的草稿发布工作流。
3. **指导素材允许公共访问**：仅 `guidance/` 前缀下的教学视频、封面、步骤图和错误示意资源可使用公共对象地址/CDN；患者视频、报告附件、反馈图片、关键点等患者数据必须保持私有并经鉴权访问。
4. **优化优先级**：先保证上传—分析—回调—报告的状态一致性和可恢复性，再强化算法质量门控，最后补齐自动化验证和云上演练。

## M0：安全封锁

### M0.1 生产环境硬门禁

**目标**：生产进程不得带着开发 Mock、默认密钥、HTTP 回调或本地代理存储启动。

**改动范围**：

- `services/main-service/src/common/runtime/environment.ts`：新增主服务生产配置校验；
- `services/main-service/src/main.ts`：启动前执行校验，并禁止生产静态暴露本地患者资产；
- `services/analysis-service/app/core/config.py`、`app/main.py`：新增分析服务生产配置校验；
- `.env.example`、`services/analysis-service/.env.example`：明确开发模板身份，并补充生产环境必填说明。

**验收**：生产环境使用默认 token、Mock、HTTP 回调、`local_proxy` 或本地患者资产暴露配置启动时失败；开发环境不受影响。

### M0.1a 密钥治理收尾（本轮暂缓实施）

**当前决定**：不立即改动 `.env.production`、`.env.example` 或现网密钥，避免在部署切换前造成环境不可用。

**后续执行清单**：

1. 由部署负责人一次性轮换微信 AppSecret、OSS RAM 凭据、MySQL/Redis 密码、JWT Secret 与分析内部 Token；
2. 将跟踪的环境模板中的真实值替换为占位符；
3. 在 CI 增加 Secret 扫描，并确认历史仓库、构建日志与部署备份的清理策略；
4. 将生产密钥迁移至 Secret Manager 或 CI/CD Secret 注入，禁止通过仓库和镜像分发。

**出口**：新旧密钥切换、生产回归与回滚预案均已演练；仓库追踪文件不再包含真实 Secret。

### M0.2 管理端账号与令牌安全

**目标**：登录只验证已有账户；角色只从数据库读取；生产环境不接受 Mock token。

**改动范围**：

- `services/main-service/src/auth/auth.service.ts`：删除登录自动建号、角色推断和默认 JWT/回调密钥；
- `services/main-service/src/admin/bootstrap-admin.ts`：新增显式的一次性初始管理员引导命令；
- `services/main-service/package.json`：增加引导命令；
- `services/main-service/src/admin/admin.controller.ts`：加强管理员密码最低要求及自我降权/禁用保护。

**验收**：不存在账号登录返回未授权；账号角色不因用户名变化；生产无强密钥不能启动；首次管理员只能通过显式引导命令创建。

### M0.3 患者资产与上传校验

**目标**：患者视频不能由静态目录公开访问，上传进入服务端后有大小、类型与文件头基础校验；教学指导素材可按公共资源策略分发。

**改动范围**：

- `main.ts`、`storage.service.ts`、视频/反馈控制器及服务；
- 明确教学公共素材与患者私有资产的不同访问路径；
- 仅允许 `guidance/` 前缀资源使用公共 CDN/对象地址，其他资产拒绝公共读取；
- 对患者视频和反馈图片继续执行归属校验、类型、大小和文件头校验。

**验收**：生产不会挂载 `/oss-assets/videos/*`；`guidance/` 素材可稳定公开播放；伪装文件、超限文件和不支持类型被拒绝；患者资产访问仍受归属校验。

## M1：可靠主链路

### M1.1 上传确认与任务投递状态机

1. 将确认上传的合法前置状态限定为 `uploading`；同一请求重复提交时仅返回既有任务状态，不得改写 `action_type`、时长、对象路径或重复累计训练日；
2. 确认上传时校验对象存在、视频归属、预签发动作类型与请求动作类型一致；
3. 将状态迁移收敛为 `uploading → queued → processing → completed | quality_insufficient | review_required | failed`，拒绝任何终态回退；
4. 所有视频 ID 路由参数统一使用正整数校验，避免 `NaN`、小数和超大整数进入 `BigInt` 查询。

### M1.2 分析运行与回调幂等

1. 增加 `analysis_run`：每次投递和重新分析生成独立运行 ID，保存 provider task ID、请求快照、算法/模板版本、开始/结束时间和最终状态；
2. 回调携带 `videoId + analysisRunId + providerTaskId + timestamp + nonce + HMAC`，主服务校验签名、时效、任务归属及状态迁移；
3. 将结果落库、患者可见状态变化和副作用事件放在受控事务中；重复回调只确认成功，不重复生成报告、通知、徽章和激励；
4. 回调失败写入 `callback_outbox`，按退避策略重试；补偿扫描采用数据库领取/锁定，避免多 Beat/Worker 重复投递；
5. `review_required` 与其他终态同样写入 `finished_at`，并在状态、历史、报告和管理端任务列表中统一展示。

### M1.3 不改变当前指导内容产品模型的修复

1. 保留“保存完整版本 + 启用/下线”模型，不引入草稿接口或草稿状态；
2. 移除患者 `GET /guidance/by-action/:actionType` 中的下线写操作，读接口必须无副作用；
3. 启用内容时通过事务和数据库约束保障同一 `action_type` 最多一条 `status=1`；并发冲突返回可理解错误，由管理员刷新后重试；
4. 版本历史继续保留为审计/回滚来源，`published_version` 统一解释为当前保存版本，不承担草稿语义。

**出口**：重复确认不改写历史视频；同一视频任意重复/乱序回调只产生一个终态；同动作始终只有一条启用内容；读指导内容不会改变数据库。

## M2：算法安全输出

### M2.1 质量门控与缺失数据处理

1. 视频流、时长、帧率、抽样画面任一关键质量信息无法确认时，直接进入 `quality_insufficient` 或 `review_required`，不得继续产出确定性评分；
2. 低分辨率、低帧率、过短/过长视频作为明确拒绝条件，而不是仅记录 issue；
3. 关键点插值只允许连续缺失不超过 `MAX_INTERPOLATE_GAP` 的区间；超长缺失段保持缺失并降低关键点可靠性；
4. 质量评分加入关键关节、关键动作阶段的有效帧比例和连续缺失率，不能只使用全局平均可见度；
5. 统一修正采样逻辑，以实际时间间隔抽帧，避免不同源 FPS 对阶段切分产生系统性偏差。

### M2.2 结果降级与人工复核

1. 模板/特征缺失、维度冲突、异常分布和低置信度统一进入 `review_required`；
2. `quality_insufficient` 不返回评分或等级，仅返回可理解的重拍指引；
3. `review_required` 显示“需要进一步确认”，报告、历史记录和通知使用一致文案；
4. 人工复核结果保留原算法快照、复核人、时间、依据和患者可见文本；
5. 分析查询接口返回真实质量、置信度和版本字段，禁止用固定默认值填充。

### M2.3 阈值受控

1. 分析服务仅接受主服务读取的受控模板快照；限制 `sigma_multiplier` 等参数的范围、类型和动作适用性；
2. 每次结果关联算法版本、模板版本、阈值版本和分析运行 ID；
3. 建立专家标注回归集，覆盖不同动作、角度、亮度、帧率与缺失场景，并据此校准阈值。

**出口**：质量不足、低置信度、模板缺失和异常结果均不展示确定性动作等级；长缺失轨迹不会被伪造插值为有效动作。

## M3/M4：云上生产与可验证发布

### M3.1 基础设施与可观测性

1. 服务 Dockerfile、私网部署、HTTPS Ingress、KMS/Secret Manager；
2. MySQL/对象存储备份及恢复演练，Redis 持久化和任务恢复；
3. 为上传、投递、Worker、回调、报告和人工复核贯穿 `traceId`；监控队列积压、分析耗时、质量拒绝率、回调重试/死信、待复核积压和接口错误率；
4. 分析 API readiness 增加 MySQL、Redis/Broker、关键表结构和对象存储连接的受控检查；
5. 在 staging 对 Worker CPU/内存、最大时长、最大帧数进行基准测试后再确定生产资源规格。

### M4.1 自动化质量门禁

1. Node/Python 单元测试：状态机、质量门控、插值边界、阈值校验、签名校验；
2. MySQL + Redis + MinIO 集成测试：上传、确认、Celery 任务、回调、重复/乱序回调、补偿恢复和报告展示；
3. 指导内容契约测试：保存版本、启用/下线、同动作唯一启用、公共素材地址和患者端读取；
4. 小程序静态检查/微信开发者工具构建门禁，以及患者 A/B 数据归属 E2E；
5. CI 执行 Prisma migration 验证、Docker Compose 启动、健康检查、镜像扫描与 staging 冒烟；
6. 预发布执行备份恢复、Worker/Beat 重启、回调断网、旧镜像回滚演练。

**出口**：发布闸门自动执行，故障、备份、恢复和回滚演练通过。

## M5：合规与临床准入

由业务、医疗、合规、信息安全责任人共同完成：知情同意、数据留存/删除、医疗边界、法规适用性、专家验证、内测/开放审批。

**出口**：组织审批完成，患者开放范围与责任边界被正式确认。
