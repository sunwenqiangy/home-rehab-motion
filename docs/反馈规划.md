
# 一、产品定位与边界

## 1.1 反馈系统定位

反馈系统不是在线问诊、客服聊天或远程医疗平台，而是：

> **围绕某次训练记录的轻量化训练问题工单系统。**

仅处理以下低风险训练相关问题：

- 看不懂报告；
- 不确定动作是否符合指导；
- 上传、分析、页面等使用问题；
- 对训练内容或操作流程的建议。

不处理：

- 症状判断；
- 疾病诊断；
- 用药建议；
- 治疗方案调整；
- 紧急求助；
- 医护即时在线咨询。

## 1.2 核心原则

1. **一条训练问题对应一张工单**：围绕同一次训练报告持续沟通。
2. **单工单多轮追问**：患者补充问题、医护追加说明都在同一工单内。
3. **患者不用等在线客服**：明确提示“非实时服务”，避免形成即时响应预期。
4. **身体不适先安全分流**：系统即时提示就医，不把风险转成普通人工待办。
5. **减少医护负担**：普通工单支持模板回复、批量关闭、低频处理。
6. **状态简单清晰**：患者只需理解“已收到、处理中、已回复、已关闭”。

# 二、反馈类型与处理策略

建议将反馈类型统一为以下五类，和当前 PRD 保持一致：

| 类型代码 | 患者展示 | 是否进入人工队列 | 默认处理方式 |
|---|---|---:|---|
| `report_unclear` | 看不懂报告 | 是 | 医护解释报告中的训练提示 |
| `action_uncertain` | 动作不确定 | 是 | 医护提供动作指导或回看指导页建议 |
| `upload_issue` | 上传或分析问题 | 是 | 运营/技术人员排查上传、分析状态 |
| `other` | 其他训练相关问题 | 是 | 人工判断、模板回复或关闭 |
| `physical_discomfort` | 身体不适 | 否 | 自动安全分流、留档、按需查看 |

## 身体不适：安全分流规则

患者选择“身体不适”后：

1. 提交前立即弹出二次确认；
2. 页面常驻展示安全提示；
3. 提交成功后自动生成一条**系统安全回复**；
4. 工单状态直接为`已关闭`或专用的`安全分流已完成`；
5. 不进入普通人工待办、不计入待回复数量；
6. 管理端只作为安全事件留档，可筛选、查看；
7. 不开放患者继续在此工单追问症状；
8. 如患者仍有不适，页面只引导其暂停训练并线下就医。

建议患者文案：

> 您提到训练中出现身体不适。请先暂停本次训练，并尽快联系您的主治医生或前往医疗机构评估。  
> 本系统仅提供训练指导，不能提供诊断、紧急医疗帮助或治疗建议。

# 三、工单状态与流转

## 3.1 对患者展示的状态

| 状态 | 含义 | 患者可操作 |
|---|---|---|
| `待处理` | 已收到，等待工作人员查看 | 可补充内容 |
| `处理中` | 工作人员正在处理 | 可补充内容 |
| `已回复` | 已收到最新说明 | 可继续追问 |
| `已关闭` | 当前问题已结束 | 不可继续追问，可从报告页新建 |

## 3.2 内部状态规则

```text
患者创建普通反馈
  ↓
待处理
  ↓ 医护领取 / 开始处理
处理中
  ↓ 医护发送回复
已回复
  ↓ 患者追问或补充
待处理
  ↓ 最后一条消息超过 7 天
可关闭
  ↓ 医护手动、批量关闭或定时任务自动关闭
已关闭
```

### 关键约束

- 患者每次补充后，工单重新变为`待处理`；
- 医护只要发送一条有效回复，工单进入`已回复`；
- 医护不能在没有回复内容的情况下直接把普通工单标记为`已回复`；
- `已关闭`的普通工单禁止继续发送消息；
- 患者如有新问题，从报告页创建新工单；
- 身体不适工单不走上述流程，走系统安全分流并直接结束。

## 3.3 7 天关闭规则

以`lastMessageAt`为准，而不是工单创建时间：

- `已回复`状态下，最后一条消息超过 7 天：进入“可关闭”筛选范围；
- 管理端提供“关闭 7 天未跟进的已回复工单”批量操作；
- 定时任务每日执行一次，可自动关闭符合条件的工单；
- 自动关闭时记录系统操作日志，但**不再给患者额外发通知**，避免产生无意义打扰；
- 患者在关闭前新增消息，则取消自动关闭资格并回到`待处理`。

# 四、数据模型方案

当前数据结构把`reply`直接放在反馈对象上，只支持一问一答。要支持多轮工单，需要拆分“工单”和“消息”。

## 4.1 `feedback_ticket`：反馈工单

| 字段 | 说明 |
|---|---|
| `id` | 工单 ID |
| `userId` | 患者 ID |
| `videoId` | 关联训练视频 ID |
| `reportId` | 可选，关联报告 ID |
| `type` | 反馈类型 |
| `channel` | 来源：`report` / `history` 等 |
| `status` | 待处理 / 处理中 / 已回复 / 已关闭 |
| `priority` | 普通 / 高 |
| `handlingMode` | `manual` / `safety_auto` |
| `subject` | 工单摘要，如“报告疑问” |
| `lastMessageAt` | 最后一条消息时间 |
| `firstRepliedAt` | 首次人工回复时间，可选 |
| `closedAt` | 关闭时间，可选 |
| `closedBy` | 关闭人：医护 ID 或 `system` |
| `closeReason` | `resolved` / `inactive_7d` / `safety_diversion` |
| `createdAt` / `updatedAt` | 创建、更新时间 |

## 4.2 `feedback_message`：工单消息

| 字段 | 说明 |
|---|---|
| `id` | 消息 ID |
| `ticketId` | 所属工单 ID |
| `senderRole` | `patient` / `staff` / `system` |
| `senderId` | 发送者 ID；系统消息为空 |
| `messageType` | `text` / `safety_notice` / `status_change` |
| `content` | 消息内容 |
| `images` | 图片稳定 URL 列表，最多 3 张 |
| `templateCode` | 可选，使用的标准话术模板 |
| `createdAt` | 发送时间 |

### 为什么要拆分

- 一张工单可有多轮沟通；
- 支持真实聊天式时间线；
- 能保留医护多次回复与系统提示；
- 后续可增加模板、审计、附件、撤回规则，而不污染工单主表；
- 页面只渲染消息列表，不再通过`reply`字段拼凑“对话”。

## 4.3 `feedback_status_log`：状态审计日志

| 字段 | 说明 |
|---|---|
| `id` | 日志 ID |
| `ticketId` | 工单 ID |
| `fromStatus` | 原状态 |
| `toStatus` | 新状态 |
| `operatorRole` | 患者 / 医护 / 系统 |
| `operatorId` | 操作人 ID |
| `reason` | 状态变化原因 |
| `createdAt` | 操作时间 |

该表不直接给患者展示复杂后台信息，但可用于生成准确的处理进度与管理审计。

# 五、患者端方案

## 5.1 报告页入口

入口继续放在报告页底部，文案避免“联系医护”：

- 主标题：`对本次训练有疑问？`
- 说明：`您可以提交训练相关问题。工作人员会在消息中心通知处理结果。`
- 按钮：`提交训练反馈`

表单字段：

| 字段 | 规则 |
|---|---|
| 反馈类型 | 必选，五类类型 |
| 详细描述 | 必填，3～500 字 |
| 图片 | 选填，最多 3 张 |
| 安全提示 | 常驻展示 |
| 身体不适确认 | 仅选择身体不适时出现 |

普通反馈提交成功：

> 已收到您的问题。工作人员将在方便时处理，处理结果会通过消息中心通知您。

建议补充服务承诺说明，但避免具体时效承诺：

> 本系统不是实时咨询服务，请留意消息中心的处理提醒。

## 5.2 身体不适二次确认

当患者选择`身体不适`并点击提交：

- 不直接提交；
- 先出现安全弹窗；
- 主操作：`我已知晓，提交记录`
- 次操作：`返回并修改类型`

安全弹窗不应写“等待医护回复”，而应明确：

> 请先暂停训练。若疼痛、不适持续、加重或影响活动，请及时联系主治医生或前往医疗机构评估。

提交后展示：

- 系统安全提示；
- “该记录已保存”；
- `查看安全提示`；
- `返回首页`或`查看训练报告`。

不提供“继续追问”按钮。

## 5.3 反馈详情页

普通工单采用“工单信息 + 消息流”结构：

1. 顶部状态卡：
   - 类型；
   - 当前状态；
   - 关联训练；
   - 最后更新时间。

2. 处理进度：
   - 已收到；
   - 处理中；
   - 已回复；
   - 已关闭。

3. 消息时间线：
   - 患者原始问题；
   - 患者补充；
   - 医护回复；
   - 系统状态提示；
   - 图片附件。

4. 底部操作：
   - `待处理` / `处理中` / `已回复`：展示“补充问题”输入框；
   - `已关闭`：展示“本次问题已结束。如对训练报告有新问题，可返回报告页重新提交反馈。”

5. 关联报告入口：
   - 始终保留，便于患者回看当前训练上下文。

## 5.4 患者追问规则

- 每次可输入文字并上传最多 3 张图片；
- 发送后自动新增一条`patient`消息；
- 工单状态改为`待处理`；
- 更新`lastMessageAt`；
- 通知医护端待办数增加；
- 患者不能修改或删除已发送内容；
- 已关闭工单不允许追问。

# 六、管理端方案

## 6.1 两个队列，而不是所有记录混在一起

### A. 普通待办队列

默认展示需要人工处理的普通工单：

- `待处理`
- `处理中`
- 患者在`已回复`后重新追问的工单

排序规则：

1. `待处理`优先于`处理中`；
2. 患者最后消息时间越早越靠前；
3. 可按类型、患者、训练动作、日期筛选；
4. 默认不展示已关闭工单。

### B. 安全分流记录

单独菜单或筛选页，避免与普通待办混淆：

- 类型为`身体不适`；
- 已自动向患者提示暂停训练和就医；
- 默认不需要人工处理；
- 可按日期、患者、关联训练筛选；
- 管理员可查看留档，但不设置“回复 SLA”；
- 如确有必要，工作人员可发送受限的安全模板消息。

## 6.2 工单详情页

管理端详情应包含四个区域：

| 区域 | 内容 |
|---|---|
| 患者与训练上下文 | 患者昵称、训练次数、关联动作、报告分数、报告摘要 |
| 工单概览 | 类型、状态、来源、创建时间、最后消息时间 |
| 对话时间线 | 患者问题、图片、医护回复、系统状态事件 |
| 处理面板 | 状态操作、模板回复、发送回复、关闭工单 |

## 6.3 医护处理动作

建议不要提供“任意选状态 + 随意填回复”的组合框，而是拆成明确动作：

| 操作 | 前置状态 | 系统行为 |
|---|---|---|
| 开始处理 | 待处理 | 状态改为处理中，记录操作日志；不通知患者 |
| 发送回复 | 待处理 / 处理中 / 已回复 | 新增医护消息，状态改为已回复，通知患者 |
| 关闭工单 | 已回复 | 状态改为已关闭，记录关闭原因 |
| 批量关闭 | 已回复且 7 天无新消息 | 批量关闭，记录为系统或当前医护操作 |
| 查看安全记录 | 安全分流 | 只读为主，必要时允许发送安全模板 |

## 6.4 回复模板

为减少医护工作量，内置可编辑模板：

| 场景 | 模板方向 |
|---|---|
| 看不懂报告 | 用患者可理解语言解释评分和“下一步怎么做” |
| 动作不确定 | 引导回看动作指导、拍摄要求、常见错误 |
| 上传问题 | 告知检查网络、视频时长、重新提交方式 |
| 无法处理 | 告知当前系统能力边界，并给出可执行下一步 |
| 身体不适 | 固定安全模板：暂停训练、联系主治医生或就医 |

模板只能作为初稿，普通反馈可编辑；身体不适仅允许安全模板或受限编辑，以避免诊断性表述。

# 七、通知方案

## 7.1 患者通知

只在以下事件触发，且**一次事件只发一条通知**：

| 触发事件 | 通知标题 | 跳转 |
|---|---|---|
| 普通反馈创建成功 | 已收到您的训练反馈 | 工单详情 |
| 医护回复 | 您的训练反馈有新回复 | 工单详情 |
| 工单关闭 | 您的问题已处理完成 | 工单详情 |
| 身体不适提交 | 请先暂停训练并及时就医 | 安全分流详情 |

不建议为“状态变更”和“处理进展”分别创建两条消息；消息中心应服务于患者行动，而不是展示内部事件流水。

## 7.2 管理端待办提醒

管理端只需要轻量提醒：

- 顶部显示普通`待处理`数量；
- 列表显示“患者最后留言时间”；
- 患者追问后进入待处理队列；
- 安全分流记录不计入普通待办；
- 不需要即时弹窗、声音提醒或复杂 SLA 倒计时。

这更符合“医护人员没有太多时间处理反馈”的实际情况。

# 八、接口设计

建议将现有一问一答接口逐步改为工单与消息模型。

## 患者端

| 方法 | 路径 | 用途 |
|---|---|---|
| `POST` | `/api/v1/feedback/tickets` | 创建普通反馈工单或安全分流记录 |
| `GET` | `/api/v1/feedback/tickets` | 获取我的工单列表 |
| `GET` | `/api/v1/feedback/tickets/:id` | 获取工单、消息、状态记录、关联训练摘要 |
| `POST` | `/api/v1/feedback/tickets/:id/messages` | 在未关闭普通工单下追加问题 |
| `GET` | `/api/v1/feedback/templates/safety` | 可选，获取安全提示文案 |

## 管理端

| 方法 | 路径 | 用途 |
|---|---|---|
| `GET` | `/api/v1/admin/feedback/tickets` | 获取普通队列，支持状态、类型、患者、日期筛选 |
| `GET` | `/api/v1/admin/feedback/safety-records` | 获取安全分流记录 |
| `GET` | `/api/v1/admin/feedback/tickets/:id` | 获取完整工单详情 |
| `POST` | `/api/v1/admin/feedback/tickets/:id/start` | 开始处理 |
| `POST` | `/api/v1/admin/feedback/tickets/:id/messages` | 发送医护回复 |
| `POST` | `/api/v1/admin/feedback/tickets/:id/close` | 手动关闭 |
| `POST` | `/api/v1/admin/feedback/tickets/batch-close` | 批量关闭 7 天无消息的已回复工单 |
| `GET` | `/api/v1/admin/feedback/reply-templates` | 获取回复模板 |

## 系统任务

| 任务 | 执行频率 | 行为 |
|---|---|---|
| 自动关闭任务 | 每日一次 | 关闭已回复且 7 天无消息的普通工单 |
| 图片清理/校验任务 | 定期 | 清理失败上传临时资源、检查图片 URL 有效性 |
| 安全分流留档检查 | 可选 | 仅统计，不触发人工待办 |

# 九、图片上传方案

不能将微信临时路径直接保存为反馈附件。推荐复用现有对象存储预签名上传机制：

1. 患者选择图片；
2. 小程序请求反馈图片上传凭证；
3. 小程序直传对象存储；
4. 上传成功获得稳定 `url` / `objectKey`；
5. 创建工单或发送消息时提交稳定图片 URL；
6. 服务端校验图片数量、来源与所属患者；
7. 工单详情页通过稳定 URL 预览。

限制建议：

- 最多 3 张；
- 单张最大 5 MB；
- JPEG、PNG、WebP；
- 服务端记录文件类型、大小、上传人和上传时间；
- 不允许患者借用他人的对象存储地址。

# 十、实施优先级

## P0：先把普通工单闭环做正确

1. 将`feedback`拆为工单与消息；
2. 实现单工单多轮追问；
3. 实现严格状态流转；
4. 解决已关闭工单不可继续追问；
5. 管理端支持开始处理、回复、关闭；
6. 患者端按消息流展示工单详情；
7. 合并重复的患者通知。

## P1：补齐安全和效率

1. 身体不适自动安全分流；
2. 安全分流不进入人工待办；
3. 回复模板；
4. 7 天无消息批量关闭与自动关闭；
5. 管理端筛选、排序和待办数量；
6. 图片真实上传到对象存储。

## P2：运营与审计增强

1. 回复模板使用统计；
2. 工单类型、处理时长、关闭率统计；
3. 异常反馈关键词辅助提示；
4. 医护角色与模板权限；
5. 导出留档、审计日志查询。

# 十一、验收标准

完成后应满足以下可验证结果：

1. 患者针对一份训练报告创建工单后，可在同一详情页连续补充两次问题，医护可分别回复，消息按时间顺序完整展示。
2. 患者每次追问后，工单自动从`已回复`回到`待处理`。
3. 医护回复后，工单自动变为`已回复`，患者收到且只收到一条可直达工单的通知。
